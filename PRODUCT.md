# BeanFeature Lab — продуктовый и научный контекст

## Platform

web

## Stack

- Frontend: Next.js и TypeScript; Node.js 24 LTS.
- Backend/API: Python 3.11 и FastAPI.
- ML и анализ данных: pandas, NumPy, scikit-learn, XGBoost, LightGBM.
- Визуализация научных данных: Plotly.
- UI: MUI Core, MUI X Data Grid Community и Tabler Icons. Lucide и MUI X Pro/Premium не используются; для научных графиков применяется Plotly, не MUI Charts.
- Метаданные, конфигурации и результаты экспериментов: SQLite.
- Научные raw/processed datasets, обученные модели и тяжёлые ML-артефакты: файловое хранилище внутри структуры проекта.

Основной продукт — веб-приложение с отдельными frontend и backend. Streamlit не используется как основной интерфейс. CLI может быть вспомогательным инструментом для воспроизводимых запусков. Стандартные элементы интерфейса берутся из MUI; собственный UI kit не создаётся. Специальные компоненты допустимы для исследовательских представлений, которые нельзя разумно собрать из готовых компонентов.

## Назначение

BeanFeature Lab — веб-приложение, научно-исследовательский инструмент и ML/data-analysis dashboard для проведения и анализа экспериментов по классификации сортов фасоли. Основная цель — исследовать, как число доступных морфологических признаков влияет на качество классификации, и определить минимальный бюджет **исходных измеряемых признаков**, при котором качество остаётся близким к модели на всех 16 признаках. Конкретное достаточное число признаков, состав набора и лучшая модель пока неизвестны.

Главный сценарий: пользователь сравнивает модели и методы отбора при разных значениях `k`, изучает качество, устойчивость выбранных признаков и вычислительную стоимость, затем оценивает компромисс между качеством классификации и сложностью системы. Это рабочий интерфейс для исследования (режим Operate), а не маркетинговая страница.

## Пользователи

- Студент или автор исследования проводит воспроизводимые эксперименты и готовит научные выводы.
- Исследователь проверяет протокол, сравнивает методы и изучает устойчивость результатов.
- Преподаватель или член комиссии изучает результаты, исходные условия и ограничения выводов.

## Научная основа

Основной набор данных — **UCI Machine Learning Repository — Dry Bean Dataset — Dataset ID 602**. Согласно исходному докладу, он содержит 13 611 объектов, семь классов (`Seker`, `Barbunya`, `Bombay`, `Cali`, `Dermosan`, `Horoz`, `Sira`) и 16 численных морфологических/геометрических признаков, полученных после сегментации изображений семян; в описании набора указано отсутствие пропусков. Это сведения из доклада, а не результат проверки загруженного датасета в проекте.

Главная исследуемая переменная — число исходных признаков `k = 1…16`. Гипотеза об избыточности части геометрических признаков подлежит проверке. PCA рассматривается отдельно: `k` компонент PCA показывает размерность нового представления и **не** означает, что достаточно измерить `k` исходных физических параметров. Цветовые, текстурные, спектральные признаки и другие датасеты в основной табличный эксперимент не входят; доклад описывает их как возможные расширения.

## Планируемый экспериментальный протокол

В утверждённом baseline на всех 16 признаках участвуют Logistic Regression, SVM RBF, Random Forest, XGBoost, LightGBM и небольшая MLP. Обязательная полная кривая `k = 1…16` с Mutual Information включает первые пять моделей; MLP остаётся в baseline и Extended. Контрольные сравнения ANOVA, RFE и tree-based importance выполняются на ограниченном наборе моделей и заранее зафиксированных в конфигурации точках `k`. L1 Logistic Regression сохраняет фактический набор и число ненулевых признаков по каждому fold. PCA — отдельная ветвь с `1…16` компонентами. Correlation pruning, Sequential Feature Selection, дополнительные ablation-проверки, внешние данные и raw images остаются расширениями.

Рекомендуемая схема оценки — nested stratified cross-validation с одинаковыми внешними разбиениями для сравниваемых вариантов: внешний `RepeatedStratifiedKFold` с 5 folds и 3 повторами, внутренний `StratifiedKFold` с 4 folds и перемешиванием. Вся подготовка данных, масштабирование, отбор признаков, настройка гиперпараметров и при необходимости калибровка должны обучаться только на соответствующих обучающих folds. Внешний test fold нельзя использовать для выбора признаков, модели или параметров.

Для научной кривой каждое `k` является заранее заданным экспериментальным условием. Оценка процедуры автоматического выбора конечной системы — отдельная задача, где `k`, метод отбора и модель выбираются внутри внутренней CV. Эти две оценки нельзя смешивать.

## Оценка и воспроизводимость

Основная метрика — **macro-F1**. Обязательны accuracy, recall по каждому классу и confusion matrix; multiclass macro ROC AUC one-vs-rest диагностическая при корректной основе для расчёта. Calibration, log loss и multiclass Brier score остаются Extended, если не требуются для конкретного анализа вероятностей. Инженерные показатели: wall-clock время fit/search, latency полного preprocessing + model pipeline для одной строки и пакета, пик памяти, размер сериализованного pipeline и устойчивость выбора признаков между folds. Latency и память измеряются с повторами, warm-up и сохранением hardware/software условий.

Результаты должны быть воспроизводимыми: фиксируются версия и происхождение датасета, версия среды и зависимостей, конфигурации, random seeds, разбиения, параметры, обученные артефакты и полученные метрики. Основной заранее заданный порог достаточности — абсолютная потеря macro-F1 не более `0.01` относительно сопоставимого 16-признакового baseline той же модели на одинаковых outer folds, с учётом оценки неопределённости для зависимых repeated-CV результатов. Margin не меняется после просмотра данных; метод интервала ещё требуется определить. One-standard-error rule — sensitivity analysis, Pareto — дополнительная инженерная интерпретация. Отсутствие подходящего `k < 16` допустимо.

**На данный момент нет результатов собственных экспериментов.** Значения macro-F1, accuracy, ROC AUC, времени, памяти, оптимального `k`, выбранных признаков и вывод о лучшей модели остаются неизвестными до реальных запусков. Иллюстративные числа и результаты, опубликованные другими авторами, нельзя выдавать за результаты BeanFeature Lab. Запрещены фиктивные метрики и демонстрационные «результаты», похожие на измеренные.

## Программный продукт и границы

Доклад предлагает два разных слоя будущего продукта:

1. **Исследовательский experiment runner** — воспроизводимо выполняет протокол, сохраняет условия, артефакты и реальные результаты. В докладе CLI/скрипты названы эталонной реализацией воспроизводимого эксперимента.
2. **Демонстрационный classifier** — применяет уже обученную и проверенную модель к валидным табличным входным данным и показывает предсказание с метаданными модели. Он не заменяет эксперимент и не должен создавать научные результаты из демонстрационных значений.

Для интерфейса доклад предлагает Streamlit как возможный вариант, но для BeanFeature Lab утверждено полноценное веб-приложение с отдельными Next.js frontend и FastAPI backend. CLI остаётся возможным вспомогательным инструментом воспроизводимого исследования. Способ развёртывания пока не определён. На текущем этапе не создаются приложение, API, ML-пайплайн, схема хранения, графики и модели.

## Научные ограничения

- Выводы по UCI Dry Bean относятся к исследованному набору и семи представленным сортам. Обобщение на другие партии, камеры, освещение, регионы и годы требует независимой внешней проверки.
- Табличный набор уже прошёл сегментацию и извлечение признаков; устойчивость классификатора и устойчивость измерительного конвейера — разные вопросы.
- Коррелированные и производные признаки могут взаимозаменяться между folds. Устойчивость состава набора нужно анализировать отдельно от качества классификации.
- Сравнение результатов разных датасетов и разных разбиений не даёт честного сравнения моделей. Утверждение о мировой первизне такого отбора признаков без отдельного обзора литературы недопустимо.

## Материалы и открытые решения

Основной источник постановки: `docs/research/Влияние_количества_признаков_семян_фасоли_на_точность_их_классификации.docx`. Исходный датасет и экспериментальные артефакты в проекте на этом этапе отсутствуют.

До экспериментальных запусков нужно зафиксировать в конфигурации контрольные точки `k`, search budget и метод интервала для зависимых repeated-CV результатов. До реализации также нужно определить способ развёртывания и детали воспроизводимости/хранения. Внешние датасеты и работа с исходными изображениями остаются отдельными возможными этапами.
