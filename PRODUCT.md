## Platform

## Stack

- Frontend: Next.js и TypeScript; Node.js 24 LTS.
- Backend/API: Python 3.11 и FastAPI.
- ML и анализ данных: pandas, NumPy, scikit-learn, XGBoost, LightGBM.
- Визуализация научных данных: Plotly.
- UI: MUI Core, MUI X Data Grid Community и Tabler Icons. Lucide и MUI X Pro/Premium не используются; для научных графиков применяется Plotly, не MUI Charts.
- Метаданные, конфигурации и результаты экспериментов: SQLite.
- Научные raw/processed datasets, обученные модели и тяжёлые ML-артефакты: файловое хранилище внутри структуры проекта.

Основной продукт — веб-приложение с отдельными frontend и backend. Streamlit не используется как основной интерфейс. CLI может быть вспомогательным инструментом для воспроизводимых запусков. Стандартные элементы интерфейса берутся из MUI; собственный UI kit не создаётся. Специальные компоненты допустимы для исследовательских представлений, которые нельзя разумно собрать из готовых компонентов.

## Назначение

BeanFeature Lab — веб-приложение, научно-исследовательский инструмент и ML/data-analysis dashboard для проведения и анализа экспериментов по классификации сортов фасоли. Основная цель — исследовать, как число доступных морфологических признаков влияет на качество классификации, и определить минимальный бюджет **исходных измеряемых признаков**, при котором качество остаётся близким к модели на всех 16 признаках. Для Core MI минимальные sufficient budgets уже рассчитаны отдельно по моделям; стабильность состава признаков продолжает анализироваться, а «лучшая модель» не объявляется простым максимумом outer-CV результатов.

Главный сценарий: пользователь сравнивает модели и методы отбора при разных значениях `k`, изучает качество, устойчивость выбранных признаков и вычислительную стоимость, затем оценивает компромисс между качеством классификации и сложностью системы. Это рабочий интерфейс для исследования (режим Operate), а не маркетинговая страница.

## Пользователи

- Студент или автор исследования проводит воспроизводимые эксперименты и готовит научные выводы.
- Исследователь проверяет протокол, сравнивает методы и изучает устойчивость результатов.
- Преподаватель или член комиссии изучает результаты, исходные условия и ограничения выводов.

## Научная основа

Основной набор данных — **UCI Machine Learning Repository — Dry Bean Dataset — Dataset ID 602**. Официальный ARFF загружен и строго проверен: 13 611 объектов, семь канонических классов (`SEKER`, `BARBUNYA`, `BOMBAY`, `CALI`, `DERMASON`, `HOROZ`, `SIRA`), 16 численных морфологических/геометрических признаков и отсутствие пропусков. Схема сохраняет точные official spellings, включая `AspectRation` и `roundness`; расхождения с прозой исходного доклада записаны в manifest, но не исправляются переименованием.

Главная исследуемая переменная — число исходных признаков `k = 1…16`. Гипотеза об избыточности части геометрических признаков подлежит проверке. PCA рассматривается отдельно: `k` компонент PCA показывает размерность нового представления и **не** означает, что достаточно измерить `k` исходных физических параметров. Цветовые, текстурные, спектральные признаки и другие датасеты в основной табличный эксперимент не входят; доклад описывает их как возможные расширения.

## Реализованный Core-протокол

В утверждённом baseline на всех 16 признаках участвуют Logistic Regression, SVM RBF, Random Forest, XGBoost, LightGBM и небольшая MLP. Обязательная полная кривая `k = 1…16` с Mutual Information включает первые пять моделей; MLP остаётся в baseline и Extended. Контрольные сравнения ANOVA, RFE и tree-based importance выполняются на ограниченном наборе моделей и заранее зафиксированных в конфигурации точках `k`. L1 Logistic Regression сохраняет фактический набор и число ненулевых признаков по каждому fold. PCA — отдельная ветвь с `1…16` компонентами. Correlation pruning, Sequential Feature Selection, дополнительные ablation-проверки, внешние данные и raw images остаются расширениями.

Реализована nested stratified cross-validation с одинаковым frozen-набором внешних разбиений для сравниваемых вариантов: внешний `RepeatedStratifiedKFold` с 5 folds и 3 повторами, внутренний `StratifiedKFold` с 4 folds и перемешиванием. Вся подготовка данных, масштабирование, отбор признаков, PCA и настройка гиперпараметров обучаются только на соответствующих обучающих folds. Внешний test fold не используется для выбора признаков, модели или параметров.

Для научной кривой каждое `k` является заранее заданным экспериментальным условием. Оценка процедуры автоматического выбора конечной системы — отдельная задача, где `k`, метод отбора и модель выбираются внутри внутренней CV. Эти две оценки нельзя смешивать.

## Оценка и воспроизводимость

Основная метрика — **macro-F1**. Сохраняются accuracy, recall по каждому классу и confusion matrix; multiclass macro ROC AUC one-vs-rest используется как диагностическая метрика при корректной основе для расчёта. Calibration, log loss и multiclass Brier score остаются Extended. Инженерные показатели включают wall-clock время fit/search, latency полного preprocessing + model pipeline для одной строки и пакета, размер сериализованного pipeline и устойчивость выбора признаков между folds. Новые runs дополнительно измеряют peak process-tree RSS в отдельном процессе с baseline, частотой sampling и hardware/software profile; старые artifacts задним числом не изменяются.

Результаты воспроизводимы: фиксируются версия и происхождение датасета, версия среды и зависимостей, immutable конфигурация, random seeds, split hashes, параметры и полученные метрики. Основной заранее заданный порог достаточности — абсолютная потеря macro-F1 не более `0.01` относительно сопоставимого 16-признакового baseline той же модели на одинаковых outer folds. Формальное решение использует one-sided Nadeau–Bengio corrected repeated-CV t-style upper bound (`n=15`, `n_test/n_train=1/4`) и Bonferroni `0.05/15` внутри семейства модели. Метод и margin зафиксированы в versioned protocol до вычисления решений. Отсутствие подходящего `k < 16` остаётся допустимым результатом.

Core MI-матрица рассчитана на официальном UCI 602: пять моделей × 16 значений `k`, а также baseline на 16 исходных признаках для пяти Core-моделей и MLP. Formal minimal sufficient `k` по сохранённым paired folds установлено как 14 для Logistic Regression, SVM RBF, Random Forest и XGBoost, и 15 для LightGBM. Эти значения относятся только к зафиксированным dataset/hash, протоколу, search spaces и margin; они не являются заявлением о «лучшей модели» и не обобщаются на внешние данные. Comparator-ветви ANOVA/RFE/tree/L1/PCA рассчитаны как 84 отдельные заранее зафиксированные conditions (18/12/18/4/32); L1 показан как variable-sparsity path, PCA — как отдельное представление. Иллюстративные числа и результаты других авторов по-прежнему запрещено выдавать за результаты BeanFeature Lab.

## Программный продукт и границы

Доклад предлагает два разных слоя будущего продукта:

1. **Исследовательский experiment runner** — воспроизводимо выполняет протокол, сохраняет условия, артефакты и реальные результаты. В докладе CLI/скрипты названы эталонной реализацией воспроизводимого эксперимента.
2. **Демонстрационный classifier** — применяет уже обученную и проверенную модель к валидным табличным входным данным и показывает предсказание с метаданными модели. Он не заменяет эксперимент и не должен создавать научные результаты из демонстрационных значений.

BeanFeature Lab реализован как отдельные Next.js frontend, FastAPI backend и локальный process-isolated worker. CLI использует тот же application layer для dataset validation, конфигураций, очереди, воспроизведения, проверки и экспорта. SQLite хранит metadata и status, а hash-verified подробные результаты и deployment models — файловые artifacts. Локальное production-представление запускается через `make presentation`; публичный режим разрешает чтение и bounded classifier prediction, но блокирует scientific write operations.

## Научные ограничения

- Выводы по UCI Dry Bean относятся к исследованному набору и семи представленным сортам. Обобщение на другие партии, камеры, освещение, регионы и годы требует независимой внешней проверки.
- Табличный набор уже прошёл сегментацию и извлечение признаков; устойчивость классификатора и устойчивость измерительного конвейера — разные вопросы.
- Коррелированные и производные признаки могут взаимозаменяться между folds. Устойчивость состава набора нужно анализировать отдельно от качества классификации.
- Сравнение результатов разных датасетов и разных разбиений не даёт честного сравнения моделей. Утверждение о мировой первизне такого отбора признаков без отдельного обзора литературы недопустимо.
